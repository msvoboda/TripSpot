# TripSpot Mobile and REST API Implementation Plan

## Overview

We will build TripSpot as a mobile first travel diary with a simple Trip -> Spots -> Photos model. First we deliver a robust offline Android app (SQLite and Room), then a multi user .NET REST API with MS SQL, and finally a simple integration so selected trips can be published to a blog. The plan keeps local data, sync logic, and UI clearly separated so that each phase is small and testable.

## Current State Analysis

Based on the TripSpotStarter project:

- Models
  - app/src/main/java/com/svobo/tripspot/data/model/Entities.kt
    - TripEntity and SpotEntity exist with basic fields (title, description, timestamps, simple SyncStatus).
    - SyncStatus enum only has PENDING, SYNCED, FAILED.
    - There is no remoteId on entities and no SpotPhotoEntity.

- Room and DAOs
  - TripSpotDatabase.kt defines Room database with TripEntity and SpotEntity.
  - Daos.kt contains TripDao and SpotDao with observeTrips, observeTrip, observeSpots, upsert, countForTrip.
  - No delete operations, no queries by syncStatus, and no DAO for photos.

- Repository and Remote API
  - TripRepository.kt exposes flows and methods createTrip and addSpot.
  - Repository writes to Room (upsert) and then calls TripSpotApi methods.
  - TripSpotApi.kt defines TripSpotApi with syncTrip and syncSpot and FakeTripSpotApi that always returns success.
  - SyncStatus is not updated based on API results. No background sync or conflict handling.

- UI and ViewModel
  - TripViewModel.kt exposes trips and spots as StateFlow, supports selecting a trip and generating demo data.
  - TripSpotApp.kt contains TripListScreen and TripTimelineScreen. GPS is shown as a placeholder text and there is no photo UI.

## Desired End State

1. Mobile app (Phase 1 to 3)
   - Full offline Trip -> Spots -> Photos diary on Android.
   - Trips and spots have remoteId and full SyncStatus set ready for server sync.
   - Spots store GPS coordinates, visited time, and support manual and automatic location fill.
   - Spot photos store thumbnails as BLOBs in SQLite so UI still works if gallery originals are deleted.

2. Backend REST API (Phase 4 and 5)
   - ASP.NET Core Web API with MS SQL tables ts_trips, ts_spots, ts_spot_photos, ts_sync_log.
   - API supports multiple users via user_id and exposes CRUD endpoints and a /sync endpoint.

3. Blog integration (Phase 6)
   - Backend can expose or publish selected trips as blog ready content using remoteUrl links to photos.

## What We Are Not Doing Now

- No maps UI, GPX import, AI features, or social features.
- No complex conflict resolution yet, only last write wins.
- No CameraX capture for photos, only selecting from gallery.
- No full public blog front end in this plan, only integration points.

## Implementation Approach

We will implement in small phases. Each phase has a clear goal, touches a limited set of files, and ends with a short manual verification. Later phases can rely on the structure and contracts defined earlier.

## Phase 1: Local Data Model and Room Refactor

### Overview

Stabilise the local data model and Room schema for TripEntity, SpotEntity, and SpotPhotoEntity, and introduce a sync ready SyncStatus enum. This phase should not significantly change UI behaviour.

### Changes Required

1. SyncStatus enum

- File: app/src/main/java/com/svobo/tripspot/data/model/Entities.kt
- Change SyncStatus to:

```kotlin
enum class SyncStatus {
    LOCAL_ONLY,
    PENDING_SYNC,
    SYNCED,
    SYNC_FAILED,
    DELETED_PENDING_SYNC,
}
```

- File: app/src/main/java/com/svobo/tripspot/data/local/Converters.kt
- Make sure converters use name and valueOf so new values are stored correctly.

2. TripEntity fields

- File: app/src/main/java/com/svobo/tripspot/data/model/Entities.kt
- Extend TripEntity:
  - Add remoteId: String?
  - Keep title, description, coverImageUri.
  - Keep createdAt and updatedAt with System.currentTimeMillis default.
  - Set default syncStatus = SyncStatus.LOCAL_ONLY.

3. SpotEntity fields

- File: app/src/main/java/com/svobo/tripspot/data/model/Entities.kt
- Extend SpotEntity:
  - Add remoteId: String?.
  - Keep title and note.
  - Add GPS fields: latitude: Double?, longitude: Double?.
  - Add locationSource: String? (values like "MANUAL" or "GPS").
  - Add locationAccuracy: Double?.
  - Keep visitedAt and orderIndex.
  - Add createdAt and updatedAt with default now.
  - Set syncStatus = SyncStatus.LOCAL_ONLY.

4. SpotPhotoEntity and DAO

- File: app/src/main/java/com/svobo/tripspot/data/model/Entities.kt
- Add new @Entity(tableName = "spot_photos") data class SpotPhotoEntity with fields:
  - id: String (primary key)
  - spotId: String
  - remoteId: String?
  - thumbnail: ByteArray (JPEG or PNG thumbnail)
  - originalUri: String?
  - remoteUrl: String?
  - caption: String?
  - orderIndex: Int
  - createdAt: Long
  - updatedAt: Long
  - syncStatus: SyncStatus

- File: app/src/main/java/com/svobo/tripspot/data/local/TripSpotDatabase.kt
  - Add SpotPhotoEntity to the entities list.
  - Add abstract fun spotPhotoDao(): SpotPhotoDao.

- File: app/src/main/java/com/svobo/tripspot/data/local/Daos.kt
  - Add SpotPhotoDao with:
    - observePhotos(spotId: String): Flow<List<SpotPhotoEntity>> ordered by orderIndex, createdAt.
    - upsert(photo: SpotPhotoEntity) with OnConflictStrategy.REPLACE.
    - delete(photoId: String).
    - deleteAllForSpot(spotId: String).

5. TripDao and SpotDao CRUD

- File: app/src/main/java/com/svobo/tripspot/data/local/Daos.kt
- Extend TripDao:
  - Add delete(id: String) query.
- Extend SpotDao:
  - Add delete(id: String).
  - Keep countForTrip(tripId: String) for orderIndex calculations.

6. Repository minimal alignment

- File: app/src/main/java/com/svobo/tripspot/data/repository/TripRepository.kt
- Make sure createTrip and addSpot set syncStatus to LOCAL_ONLY or PENDING_SYNC consistently.
- This phase can keep FakeTripSpotApi calls but does not yet need to react to the Result type.

### Success Criteria

Automated
- Android project builds successfully.
- Room generates schema with tables trips, spots, spot_photos containing the new columns.

Manual
- App launches and shows current trip list and timeline without crashes.
- Demo trip creation still works.
- SpotPhotoDao can insert and read a test photo row (can be tested via temporary code or debug).

## Phase 2: Mobile UI Flows for Trips and Spots

### Overview

Expose full Trip and Spot editing in the UI so the user can manage trips and spot timeline like in the illustration. GPS is still provided manually or as a mock value.

### Changes Required

1. TripViewModel operations

- File: app/src/main/java/com/svobo/tripspot/ui/screens/TripViewModel.kt
- Add functions:
  - createTrip(title, description, coverImageUri)
  - updateTrip(tripId, title, description, coverImageUri)
  - deleteTrip(tripId)
  - createSpot(tripId, title, note, latitude, longitude, visitedAt)
  - updateSpot(spotId, title, note, latitude, longitude, visitedAt)
  - deleteSpot(spotId)
  - selectSpot(spotId)
- Drive these via new repository methods.

2. Trip list screen

- File: app/src/main/java/com/svobo/tripspot/ui/screens/TripSpotApp.kt (TripListScreen)
- Show for each trip:
  - title and a short description
  - optional cover thumbnail (from coverImageUri or placeholder)
  - count of spots (from ViewModel or repository helper)
  - createdAt date in friendly format
  - simple sync status indicator
- Add buttons:
  - Add Trip (FAB or button) -> opens AddEditTripScreen.
  - Delete Trip (overflow or swipe) -> calls deleteTrip.
  - Tap trip -> shows TripTimelineScreen for that trip.

3. Add or edit trip screen

- New file under ui/screens, for example AddEditTripScreen.
- Input fields:
  - Title (required)
  - Description (optional)
  - Cover image URI (text field or simple selector placeholder)
- Behaviour:
  - When editing, pre fill from existing TripEntity and call updateTrip.
  - When creating, call createTrip.

4. Trip detail timeline

- File: TripSpotApp.kt (TripTimelineScreen)
- Show:
  - Trip title and description on top.
  - Timeline list of spots with index (1, 2, 3), title, note preview, GPS coordinates, visited time, icons for photos and note.
- Provide actions:
  - Add Spot -> goes to AddEditSpotScreen for the current trip.
  - Tap spot -> goes to SpotDetailScreen.

5. Add or edit spot screen

- New file under ui/screens, AddEditSpotScreen.
- Fields:
  - Title (required)
  - Note (optional)
  - Latitude and Longitude (plain numeric inputs for now)
  - VisitedAt (time picker or text)
- On create:
  - Repository computes orderIndex as countForTrip(tripId) + 1.
- On edit:
  - Pre fill from SpotEntity and call updateSpot.

6. Spot detail screen

- New file under ui/screens, SpotDetailScreen.
- Show:
  - Title, note
  - Latitude and longitude formatted nicely
  - Visited time
  - Placeholder area for photos (populated in Phase 3)
- Actions:
  - Edit spot -> AddEditSpotScreen.
  - Add photo -> wired up in Phase 3.

### Success Criteria

Automated
- App builds and runs with the new screens and ViewModel methods.

Manual
- User can create, edit, and delete trips.
- User can create, edit, and delete spots under a trip and see them in order on the timeline.
- Timeline visually resembles the design concept (title, description, GPS line, time, icons), even if some values are mock.

## Phase 3: Local Photos and GPS on Mobile

### Overview

Add attaching photos to spots with thumbnails stored in SQLite and basic GPS support. Picks up immediately on top of the Phase 2 UI without involving the backend.

### Changes Required

1. Photo adding and storage

- TripRepository
  - Add suspend fun addPhotoToSpot(spotId, originalUri, caption): SpotPhotoEntity.
  - Inside, load image from originalUri, downscale to reasonable size, encode to JPEG or PNG, and store bytes in SpotPhotoEntity.thumbnail.
  - Save originalUri as string and set syncStatus = LOCAL_ONLY.

- TripViewModel
  - Expose photos for a selected spot as StateFlow<List<SpotPhotoEntity>> based on SpotPhotoDao.observePhotos.
  - Add method to call addPhotoToSpot when UI picks an image.

- SpotDetailScreen
  - Render a grid or row of thumbnails from SpotPhotoEntity.thumbnail.
  - Add button Add photo which opens a gallery picker and then calls ViewModel method.

2. Manual GPS entry

- AddEditSpotScreen
  - Keep and validate latitude and longitude fields.
  - When both provided manually, set locationSource = "MANUAL" and locationAccuracy = null in SpotEntity.

3. Automatic GPS

- New helper (for example LocationProvider) that wraps Android location APIs.
- Add button Use current location on AddEditSpotScreen which:
  - Requests permission if needed.
  - On success fills latitude, longitude.
  - Sets locationSource = "GPS" and locationAccuracy from reported accuracy.

### Success Criteria

Automated
- App builds with any new location or image libraries.
- SpotPhotoEntity can be inserted and read via tests or simple debug flow.

Manual
- User can attach at least one photo to a spot and see the thumbnail in the spot detail.
- Thumbnails persist across app restarts.
- User can enter GPS coordinates manually and see them on the timeline.
- When permissions are granted, Use current location fills GPS fields correctly.

## Phase 4: REST API and MS SQL Backend

### Overview

Create a .NET REST API with MS SQL that stores TripSpot data for multiple users, following the ts_ table prefixes. This phase is backend only and does not yet change the mobile client.

### Changes Required

1. MS SQL schema

- Create tables:
  - ts_trips (id, user_id, title, slug, description, cover_photo_url, visibility, created_at, updated_at, deleted_at).
  - ts_spots (id, trip_id, title, note, latitude, longitude, visited_at, order_index, created_at, updated_at, deleted_at).
  - ts_spot_photos (id, spot_id, remote_url, caption, order_index, created_at, updated_at, deleted_at).
  - ts_sync_log (id, user_id, entity_type, entity_id, action, status, error_message, created_at).

2. ASP.NET Core Web API

- Set up DbContext and EF Core entities mapping to ts_ tables.
- Implement DTOs: TripDto, SpotDto, SpotPhotoDto, SyncRequest, SyncResponse per assignment.
- Implement controllers:
  - /api/tripspot/trips (GET, POST, GET by id, PUT, DELETE).
  - /api/tripspot/trips/{tripId}/spots (GET, POST).
  - /api/tripspot/spots/{id} (GET, PUT, DELETE).
  - /api/tripspot/spots/{spotId}/photos (GET, POST).
  - /api/tripspot/photos/{id} (PUT, DELETE).

3. Multi user handling

- For proof of concept read user_id from an HTTP header, for example X-User-Id.
- Apply user_id filter to all queries so that each user sees only their data.

### Success Criteria

Automated
- API builds and starts.
- EF migrations create the ts_ tables in MS SQL.

Manual
- Basic CRUD for trips, spots, and photos works in Swagger or Postman for different X-User-Id values.

## Phase 5: Mobile Sync With REST API

### Overview

Replace the fake TripSpotApi with a real Retrofit client and implement sync between local SQLite and the backend using SyncRequest and SyncResponse.

### Changes Required

1. Retrofit TripSpotApi implementation

- Implement TripSpotApi methods to call the backend endpoints.
- Add a sync method calling /api/tripspot/sync.

2. Sync orchestration in TripRepository

- Collect local changes where syncStatus is LOCAL_ONLY, PENDING_SYNC, or DELETED_PENDING_SYNC for trips, spots, and photos.
- Build SyncRequest with clientId, lastSyncAt, lists of entities, and deleted items.
- Send request and process SyncResponse, updating local entities:
  - Set remoteId from server IDs.
  - Update syncStatus to SYNCED on success or SYNC_FAILED on permanent errors.
  - Apply last write wins based on updatedAt.

3. UI trigger

- Add a simple manual Sync button in the app (for example in a menu or settings) that calls a ViewModel sync method.

### Success Criteria

Manual
- Creating a new trip and spots on mobile, then running sync, creates them on the backend and sets local syncStatus to SYNCED.
- Changing a trip on mobile and syncing updates the server version.
- If there is a conflicting change on server and mobile, last write wins based on timestamps.

## Phase 6: Blog Integration

### Overview

Allow publishing selected trips from the backend into an existing blog system.

### Changes Required

- Define a PublishedTripDto containing title, lead image, ordered sections per spot, and photo URLs.
- Implement backend endpoint, for example /api/tripspot/publish/{tripId}, that:
  - Reads trip, spots, and photos.
  - Builds PublishedTripDto or directly calls the blog API.
  - Stores a blogUrl or published flag on ts_trips.

### Success Criteria

- At least one trip can be published from TripSpot backend to the blog system with correct text and images.
